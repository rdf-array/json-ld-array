The 2016 talk classified FHIR observations by what they are observations of: define a class of codings by system and code, connect it to a SNOMED CT concept, and let SNOMED CT's hierarchy answer "which observations are of an arthritis?". FHIR RDF has changed since: an element's literal is fhir:v, a uri also carries fhir:l, the IRI, a repeated element such as CodeableConcept.coding is an RDF list ( … ), and a CodeableConcept may carry the concept IRIs of its codings as rdf:type arcs. The list is the problem for OWL: FHIR's own RDF page warns that RDF lists "cause problems for OWL 2" and offers a conversion script. Read over rdf-array the list is one term, and OWL-array gives a class expression a way into it, fhir:coding some (ra:member some C), so the 2016 process runs on today's data unchanged in spirit: recognizers over the codings in the list, connective tissue to SNOMED CT, DL queries over the hierarchy.

This is a working document of the rdf-array project, generated from examples/fhir/README.md by md-to-respec.py in the same repository. It is not a W3C document and has no standing anywhere.

The process, step by step

The steps of the talk, as arthritis.ttl writes them; each ## comment there has the Manchester syntax that Protégé's DL Query tab takes.

  1. A predicate ontology. fhir-min.ttl declares the classes and properties, in fhir.ttl's style but with every repeating element a list: fhir:CodeableConcept SubClassOf: fhir:coding only (ra:Sequence and ra:member only fhir:Coding), fhir:coding max 1. From that alone a reasoner knows that each blank node in a coding list is a fhir:Coding.
  2. Recognizers. A coding is recognised by its system and its code: :Coding-of-sct-69896004 EquivalentTo: fhir:system some (fhir:l value <http://snomed.info/sct>) and fhir:code some (fhir:v value "69896004"). The system is an individual now (fhir:l); the code is still a literal, so this is the one place a class is defined from a string, as in 2016 ("we can't reason about literals so we make classes for each code"). One recognizer per code, in SNOMED CT and in ICD-10.
  3. Connective tissue, through the list. fhir:coding some (ra:member some (:Coding-of-sct-69896004 or :Coding-of-icd10-M06.9)) SubClassOf: sct:69896004: a CodeableConcept one of whose codings is a recognised rheumatoid arthritis coding is an instance of the SNOMED CT concept, which is exactly the type arc FHIR's generator adds when it can. So Amy's CodeableConcept is sct:69896004 twice over, Bob's from the SNOMED CT coding in second position, Sue's from an ICD-10 code mapped to SNOMED CT. sct:69896004 EquivalentTo: sct:Rheumatoid_arthritis-disorder joins the numeric IRIs of FHIR RDF and SNOMED CT's own OWL to the 2016 extract's descriptive ones.
  4. SNOMED CT's hierarchy. The talk's queries: an observation of rheumatoid arthritis, of seronegative rheumatoid arthritis, of an arthritis (by subclass), of an inflammatory disorder with a musculoskeletal finding site (by the role-group definitions in the extract).
  5. Beyond the talk. The patient, through the Reference (fhir:subject [ fhir:l amy:asPatient ]): fhir:Patient and inverse fhir:l some (inverse fhir:subject some :Observation-of-Rheumatoid_arthritis). The shape of the list itself: whose primary coding is SNOMED CT (ra:first), which are coded in more than one system (ra:length). And in blood-pressure.ttl, a component list inside an observation, each component with its own coding list and a Quantity: fhir:component some (ra:member some (bp:Systolic-component and fhir:value some (fhir:value some (fhir:v some xsd:decimal[>= 140])))).

Findings

  • xsd:date stops HermiT. FHIR writes a date as xsd:date (and gYear, gYearMonth, time), none of which is in the OWL 2 datatype map, and HermiT refuses to load a literal of a datatype it does not know. The subjects therefore carry no fhir:birthDate. Real FHIR data will; a FHIR-to-OWL pipeline needs a reasoner with those datatypes, a custom datatype definition, or a rewrite of such literals before reasoning. Nothing to do with lists, but it will be the first thing Protégé users hit.
  • Every FHIR list holds blank nodes, since every element is one, so no list here gets the object closure of owl-array.md §6, which OWL 2 DL allows only over named individuals (rdf-array#20). some over members is unaffected, and only over members holds where an axiom gives it (every coding is a Coding), but a DL query that asks it of the data, "observations all of whose codings are ICD-10", finds nothing where it should find sue:Obs1. Worse, HermiT reads a class assertion on an anonymous individual existentially, so getSequenceInstances(fhir:Observation) returned all 16 lists and isEntailed of a class assertion on such a list answers for some individual, not this one. owlapi-array's getSequenceInstances now leaves those lists out, so it returns none of the 16 until #20 is decided; isEntailed still answers existentially for them. Naming the expansion individuals and the blank nodes inside them, inside the reasoner's view only, would settle both; that is the recommendation recorded on #20.
  • JFact 4.0.4 calls the closure inconsistent where HermiT finds it consistent; the verdict goes away when the data property assertions or the cardinality restrictions are removed, so it is JFact's datatype reasoning over fhir:v exactly 1 with literals of several datatypes. HermiT is the reference here, and the one Protégé bundles.
  • The FHIR ontology's list axioms are wrong over rdf-array, as §5 shows: allValuesFrom on a repeating element types the list. The fix is mechanical, ra:member only for every element whose maximum cardinality is *, and belongs in the generator.
