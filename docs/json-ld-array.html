JSON-LD-array is a mapping language that turns conventional JSON — the JSON an API already produces — into rdf-array. It keeps the one idea of JSON-LD that conventional JSON needs, a map from JSON keys to RDF properties, and drops the rest:

This is a working document of the rdf-array project, generated from docs/json-ld-array.md by tools/md-to-respec.py in the same repository. It is not a W3C document and has no standing anywhere.

Introduction

Design sketch, 2026-10-23 (begun as a tutorial on 2026-10-21). Implemented in jsonld.js-array (jsonld.arrayToRDF, with a playground), whose doc/rdf-array.md lists the decisions the implementation added. This document is json-ld-array.md in the organisation's meta-repository, rendered at <https://rdf-array.github.io/rdf-array/docs/json-ld-array.html>; rdf-array.md there describes the change from RDF to rdf-array. The names follow the rdf-array organisation: rdf-array is RDF whose data model has sequences as terms, and Turtle-array, SPARQL-array, ShEx-array and JSON-LD-array are its syntaxes.

  1. No legacy simplifications. A JSON-LD @context is one flat map in which prefixes, property terms, class terms, keyword aliases ("id": "@id") and processing directives (@vocab, @base, @language, @version, @protected, …) share a namespace. JSON-LD-array gives each its own place: prefixes, propertyMap, typeMap, named maps and a few named directives.
  2. Only a transformation of conventional JSON. The part of a document that produces RDF carries no directives: no @id, @type or blank node identifiers on nodes, no @value literal objects, no @graph, @index or framing. The mapping is kept apart from the data, in a document of its own or in reserved members (§4.3). Nodes are identified by an ordinary field that the mapping designates, or they are blank nodes. A graph that is not a tree still needs JSON-LD proper.
  3. No @container: @list or @set. rdf-array has sequences, so a JSON array is a sequence term, nested arrays included, and [] is the empty sequence (). Turning a sequence into repeated properties (or back) is an rdf-array operation on any data, not a mapping concern (§2.1).
  4. One construct for property mappings, propertyMap, written inline or referring by name to a map declared once at the root. At the root of the mapping it plays the role of the property definitions "sprinkled" through a conventional @context; inside a property definition or a type definition it says which keys may appear below, as a production in a grammar does (§4).

JSON-LD-array is to JSON-LD roughly what RML is to R2RML for JSON sources, but shaped like a context rather than like a set of triples maps, and without JSONPath iterators: the tree structure of the JSON is the iterator (§10, §11).

Terminology. A JSON object is a set of members, each a name/value pair ([[RFC8259]] §4). As in JSON-LD 1.1 §1.4, an object is treated as an Infra map whose entries each have a key, the member's name, and a value ([[INFRA]]). In this document "key" always means a member name in the data, and the members of the mapping document are called attributes. A key is a plain string, compared code unit by code unit ([[RFC8259]] §8.3) and never expanded as a compact IRI. "The identifier key", "the type key" and the like name a key by the role its definition gives it; what names the node or gives its classes is always that member's value.

One example end to end

The mapping, a document of its own, with the property maps written inline:

{
    "prefixes": {
      "schema": "http://schema.org/",
      "ex":     "https://example.org/ns#",
      "xsd":    "http://www.w3.org/2001/XMLSchema#",
      "rdf":    "http://www.w3.org/1999/02/22-rdf-syntax-ns#",
      "rdfs":   "http://www.w3.org/2000/01/rdf-schema#"
    },
    "base": "https://example.org/people/",
    "unmappedKeys": "error",
    "typeMap": { "Person": "schema:Person", "Organization": "schema:Organization" },
    "propertyMap": {
      "id":       { "role": "identifier", "baseTemplate": "{}/" },
      "type":     { "role": "type" },
      "name":     "schema:name",
      "age":      { "iri": "schema:age", "datatype": "xsd:integer" },
      "born":     { "iri": "schema:birthDate", "datatype": "xsd:date" },
      "homepage": { "iri": "schema:url", "valueType": "identifier" },
      "tags":     "ex:tags",
      "knows":    { "iri": "schema:knows", "valueType": "identifier",
                    "baseTemplate": "friends.ttl", "template": "#{}" },
      "address":  { "iri": "schema:address",
                    "propertyMap": { "city": "schema:addressLocality",
                                     "zip":  "schema:postalCode" } }
    }
  }

The same mapping with the property maps declared once and referred to by name, as the productions of a grammar are:

{
    "prefixes": { "schema": "http://schema.org/", "ex": "https://example.org/ns#",

    "base": "https://example.org/people/",
    "unmappedKeys": "error",
    "typeMap": { "Person": "schema:Person", "Organization": "schema:Organization" },
    "propertyMap": "rootMap",
    "namedPropertyMaps": {
      "rootMap": {
        "id":       { "role": "identifier", "baseTemplate": "{}/" },
        "type":     { "role": "type" },
        "name":     "schema:name",
        "age":      { "iri": "schema:age", "datatype": "xsd:integer" },
        "born":     { "iri": "schema:birthDate", "datatype": "xsd:date" },
        "homepage": { "iri": "schema:url", "valueType": "identifier" },
        "tags":     "ex:tags",
        "knows":    { "iri": "schema:knows", "valueType": "identifier",
                      "baseTemplate": "friends.ttl", "template": "#{}" },
        "address":  { "iri": "schema:address", "propertyMap": "addressMap" }
      },
      "addressMap": {
        "city": "schema:addressLocality",
        "zip":  "schema:postalCode"
      }

  }

The data, untouched API output:

{ "id": "alice", "type": "Person", "name": "Alice", "age": 42,
    "born": "1984-02-29", "homepage": "https://alice.example/",
    "tags": ["rdf", "json"], "knows": ["Bob", "Eve"],
    "address": { "city": "Paris", "zip": "75001" } }

The result, in Turtle-array:

<https://example.org/people/alice> a schema:Person ;
      schema:name "Alice" ; schema:age 42 ; schema:birthDate "1984-02-29"^^xsd:date ;
      schema:url <https://alice.example/> ;
      ex:tags ( "rdf" "json" ) ;
      schema:knows ( <https://example.org/people/alice/friends.ttl#Bob>
                     <https://example.org/people/alice/friends.ttl#Eve> ) ;
      schema:address [ schema:addressLocality "Paris" ; schema:postalCode "75001" ] .

Two things to notice. The id member does two jobs: its value alice, resolved against the base in force, https://example.org/people/, names the node, and through "baseTemplate": "{}/" it makes https://example.org/people/alice/ the base for the object's other members. The knows definition then sets friends.ttl, resolved against that base, as the base for its values, and the template #{} makes each value a fragment of it. And knows is an array, so it is one sequence term; an application that wants two schema:knows triples instead spreads it afterwards (§2.1).

The one principle behind arrays and dictionaries: JSON arrays are ordered, so they become sequences; JSON objects are unordered (RFC 8259), so an object used as a dictionary becomes repeated properties. Nothing in the mapping chooses between list and set; the JSON already did.

Spreading is orthogonal

Whether schema:knows ( <…#Bob> <…#Eve> ) or schema:knows <…#Bob>, <…#Eve> is wanted is a question about the RDF, not about the JSON, so JSON-LD-array does not answer it. In SPARQL-array a sequence is spread with a position pattern, over any data however it was produced:

DELETE { ?s schema:knows ?seq }
    INSERT { ?s schema:knows ?friend }
    WHERE  { ?s schema:knows ?seq . ?s schema:knows ((?friend))[*] }

and gathered back with an aggregate into a sequence. JSON-LD needed @container: @list and @container: @set because RDF 1.1 had no sequence term to leave the choice to.

A type definition

A typeMap entry is a string, the class IRI, or { "iri": …, "propertyMap": … }: a map, inline or by name, for the keys of a node declared with that type.

Processing, in five rules

  1. A JSON object is a node, and two maps govern it. Its position map is the propertyMap of the definition under which the object appears, or the root propertyMap for the root object; its type map is the propertyMap of the type definition its type key's value selects, if there is one. A map referred to by name is in scope exactly as if written inline.
  2. Identifier, base and type come first. If a key with role identifier is in scope and present, its value, resolved against the enclosing base or expanded through its template, names the node; otherwise the node is a fresh blank node (or, with termType: "blankNode" and a template, a stable one). If a key with role base, or an identifier key with a baseTemplate, is in scope and present, its value or the template's expansion, resolved against the enclosing base, is the base for the object's other members; the identifier itself resolves against the enclosing base. If a key with role type is in scope and present, its values, through the governing type maps, are the node's classes. More than one identifier key, or more than one base-setting key, present in one object is an error; one key may be both, as id is in §1. These keys are read before the others, so member order never matters (JSON-LD has the same look-ahead for @type).
  3. Every other key is looked up in the governing maps, type map first, then position map. Under "scope": "none" nothing else is in scope. Under "scope": "root" a key not found there is looked up in the root propertyMap, so the root maps serve as a global dictionary. Under "scope": "enclosing" it is looked up in each enclosing property map, nearest first, and then in the root map: lexical scoping with shadowing. A key still unmapped follows otherwise: an error, nothing, or the property vocab + key. The values of a type key are looked up the same way in the type maps, under unmappedTypes. Not looked up, and never unmapped, are the entry keys of a keyedBy dictionary, which are data; the keys inside a value whose datatype is rdf:JSON; the reserved propertyMap and mapping members of the embedded form (§4.3); and the keys whose values a template, a from reference or a group consumes (§3.5, §11).
  4. The value is converted by its JSON kind (§2) under the definition found. Arrays convert element by element into one sequence; dictionaries convert entry by entry into repeated values; flatten attaches an object's keys to the current node or makes an array's elements root nodes; inverse swaps subject and object. Arrays under inverse and under the type role spread into one triple per element instead of forming a sequence.
  5. The root value is a node if it is an object, one node per element if it is an array (there is no subject for a root sequence to hang from), and nothing if it is a scalar.

Bases and templates

The base in force starts as the root base. Each object inherits the base of the position it appears in, unless one of its keys sets a new one, by role: "base" or by a baseTemplate; that base applies to the object's other members and to everything below them. A property definition's own baseTemplate sets the base for that property's values, so a key such as knows in §1 can place its values in a document of their own. An object's identifier always resolves against the enclosing base, and the base the object sets applies to its contents, as a web page's URL and the base its links resolve against are two different things.

A template is a string with references in braces, after RFC 6570's simple string expansion:

ReferenceValue
{}the own value of the member whose definition carries the template
{key}the value of the member named key in the object the template describes (the object itself for identifier and baseTemplate on a property definition; the member's siblings for a template on a key)
{../key}the value of the member named key in the enclosing object; an array is transparent to ..
{#}the 1-based position of the element in the array that holds it, as SPARQL-array's position patterns count

A substituted value is percent-encoded as an IRI component, R2RML's IRI-safe rule, so a value holding / cannot step out of its path segment; a value substituted into a blank node label is taken as it is. A relative expansion is resolved against the base in force (RFC 3986). A template whose reference has no value produces no term, and so no triple. A member whose value is only consumed by a template needs no definition of its own.

Output

Processing yields rdf-array triples, all in the default graph. Their terms are IRIs, blank nodes, literals and sequences; a sequence holds the converted elements of one JSON array, in order.

  • In an API, a sequence is the term of the host's rdf-array data model. In the RDF/JS data model of the rdf-array forks (types-array, rdf-data-factory-array) it is { termType: "Sequence", elements: [ …terms… ], value }, where value is the N-Triples-style spelling (e1 e2 …) and DataFactory.sequence(elements) makes one; jena-array's is Node_Seq, rdflib-array's rdflib.term.Sequence.
  • As text, the output is N-Quads-array or Turtle-array: a sequence is written ( e1 e2 … ), nested freely, () when empty.
  • Blank node labels. A fresh blank node's label is the processor's choice. A stable one, from termType: "blankNode" and a template, is labelled with the expansion; a mapping whose expansions use characters outside those N-Triples allows in a blank node label produces output that a writer must relabel.
  • Numbers. The lexical form of a literal from a JSON number is the number as written in the JSON text (1.70 stays 1.70 in an xsd:decimal) when the processor's JSON parser exposes it, and otherwise the shortest spelling of the parsed number; an exponent is expanded for xsd:decimal, and xsd:double takes JSON-LD's canonical form (1.5E0).
  • IRIs are resolved against the base in force by RFC 3986 §5.2, after template values have been percent-encoded (§3.5).

A processor stops at the first error and reports it with its path, the keys and array indices from the data root to the offending value (/address/street, /phones/1/number). Errors in the mapping document are reported before any data is read, except a reference to an undeclared named map, which is reported where it is first used. Grammar first, scoping on request

A map defines the keys allowed at the position it governs, as a production in a yacc grammar defines what may appear at that point. A map referred to by name is in scope exactly as if its definitions were written inline at the reference: "propertyMap": "addressMap" and the inline object are the same mapping, and namedPropertyMaps is the grammar's table of productions. Maps may refer to one another and to themselves, so a recursive JSON shape (comments within comments) is a recursive map; the expansion is bounded because the data is finite: recursion could only be unbounded if a document implied a reference to another document, and eventually to itself, which JSON-LD-array does not do. Named maps are declared at the root only, as grammar rules are: a name then means one thing wherever it is used, and no second scoping question arises about where a name is visible. Nothing prevents relaxing this later; nothing seems to call for it.

By default ("scope": "none") a key must be in one of the two maps that govern its object, which is the strict, grammar-like reading. Two relaxations widen the lookup for mappings meant as dictionaries rather than grammars: "scope": "root" makes the root propertyMap and typeMap global, so a key unknown to the local map falls back to them; "scope": "enclosing" makes every enclosing property map visible, nearest first, with an inner definition shadowing an outer one for the same key — ordinary lexical scoping, as XML namespaces behave, where an xmlns declaration on any element is in scope for its descendants and one on the root for the document. JSON-LD 1.1's property-scoped contexts behave like "enclosing", its type-scoped contexts like a type map under "none"; its @propagate flag and "previous context" bookkeeping are what the two fixed rules replace.

The embedded form

Goal 2 is about the part of a document that produces RDF: it carries no directives. The mapping itself may travel with the data, as a conventional JSON-LD document carries its @context, through two reserved members. Any data object may contain a propertyMap member, a map or a name, which is the position map of that object (and under "scope": "enclosing" is in scope below it). The root data object may instead contain a mapping member holding a complete mapping document, with its prefixes, base, directives, named maps and root propertyMap; that is the conventional root @context, separated into its parts. An external mapping and embedded members may be combined, the embedded one being the nearer. The price of not using @ is that a data member named propertyMap (anywhere) or mapping (at the root) cannot be data; JSON-LD paid the same price with a different coin, every key beginning with @.

Decisions to confirm

  • null inside an array leaves no element, which shifts the positions after it. The alternative is an explicit placeholder term; rdf-array has none today.
  • Fractional numbers default to xsd:decimal, not JSON-LD's xsd:double; datatype gives the double back.
  • An inverse property and the type role spread an array instead of making a sequence the subject or the class. Every other array is a sequence, knows in §1 included: a mapping that wants repeated schema:knows triples spreads them afterwards (§2.1).
  • valueType: "identifier", not "iri". A value that identifies a node may name a blank node as well as an IRI once termType: "blankNode" exists, so "iri" would be a misnomer; "identifier" also mirrors role: "identifier": the role says the value identifies this node, the value type says it identifies another.
  • Strict by default. unmappedKeys defaults to { "scope": "none", "otherwise": "error" }, the grammar reading; §11 argues for "otherwise": "ignore" as the friendlier default for data from APIs that grow.
  • Named maps are root-only, like the rules of a grammar (§4.1).
  • prefixes are root-only, so a prefixed name means the same thing everywhere in the mapping; base is lexically scoped (§3.5).
  • The embedded form reserves two member names in the data, propertyMap and mapping.
  • Templates take any member of the object they describe, the enclosing object's members and the position; composing an identifier from the values of a different object still needs the structure of the JSON to put them in reach.

Names for these things

A context inside a property definition. JSON-LD 1.1 calls it a scoped context: a property-scoped context when it sits in a term definition and applies to that property's values, a type-scoped context when it sits in a class term and applies to nodes of that type. The JSON-LD API stores it in the term definition as the term's local context, and a @context written inside a node object in the data is an embedded context. In programming-language terms the behaviour under "scope": "enclosing" is lexical (static) scoping with shadowing: definitions are attached to a position in the syntax tree and visible in its subtree, as opposed to the dynamic scoping of, say, ANTLR 3's rule and global scope attributes, which follow the call chain. The default "scope": "none" is the reading of a grammar, where a production names the symbols that may follow and nothing else. Compilers call the data structure a chain of environments or nested symbol tables; attribute grammars call what is passed down an inherited attribute; XML Namespaces call the same arrangement in-scope namespaces.

A property map. JSON-LD calls the whole map a context, each entry a term definition (an expanded term definition when it is an object), and the part that names the property the term's IRI mapping; the set held by a processor is the active context's term definitions, which some implementations call the term map. RDFa Core calls the same entries term mappings. In R2RML and RML, where mappings are triples rather than JSON, the counterpart of one property definition is a predicate-object map, assembled from term maps (constant-, reference- or template-valued), and the counterpart of this whole document is a triples map. JSON-LD-array calls it a property map (propertyMap), its entries property definitions, and a map declared at the root and referred to by name a named map, the counterpart of a grammar's production.

JSON-LD, JSON-LD-array and RML side by side

RML, the RDF Mapping Language, generalizes W3C's R2RML from relational tables to CSV, XML and JSON sources. It is maintained by the W3C Knowledge Graph Construction Community Group as a family of modules (RML-Core, RML-IO, RML-CC for collections and containers, RML-FNML for functions, RML-star, RML-LV for logical views), with YARRRML as a YAML shorthand. Where JSON-LD annotates the keys of the data and JSON-LD-array maps them, RML describes the output: each triples map names a logical source and an iterator that selects records, a subject map that mints each record's subject, and predicate-object maps that emit the triples, every part of which is a term map that is constant-valued, reference-valued (a field of the record) or template-valued.

Conventions worth borrowing from RML

RML's one organizing idea is the term map: whatever part of an output triple is being produced, subject, predicate, object or graph, and in RML also the datatype and the language of a literal, it comes from a map of one of three kinds, constant, reference (a field of the current record) or template (a string with {field} references, percent-encoded when it makes an IRI). JSON-LD has only constants in the context and positions in the data. JSON-LD-array has adopted templates (§3.5); the rest of the triad, and the conventions that follow from it, are proposed here.

Implementations and tests

jsonld.js-array (rdf-array/jsonld.js-array) is the reference implementation, added to jsonld.js beside its unchanged JSON-LD processor: jsonld.arrayToRDF(data, mapping, {format}) returns RDF/JS quads, or N-Quads-array (application/n-quads) or Turtle-array (text/turtle) text; jsonld.array.parseJSON keeps the lexical form of numbers; jsonld.array.compileMapping validates a mapping once for reuse; errors carry the codes of §3.7 in details.code and the path in details.path. It implements §2 to §5 and, as extensions, every proposal of §11. Its doc/rdf-array.md records the decisions the implementation took, which this document has since adopted. A playground runs it in the browser over the examples of this document.

Tests. Every row of the tables in §5 and §11.1 is a test case: JSON data and a mapping in, the Turtle-array out, or one of the errors of §3.7. jsonld.js-array's tests/array.js holds them as mocha tests, with the error cases and malformed mappings besides. They are to move into a shared manifest of the rdf-array conformance suite (jla:ToRdfTest: mf:action the data, jla:mapping the mapping, mf:result the N-Quads-array), so that a second implementation starts from the same expectations.

A second implementation needs an rdf-array data model with the sequence term, an RFC 3986 resolver, a JSON parser that can report the source text of numbers (or the acceptance that 1.70 becomes 1.7), and a writer for N-Quads-array or Turtle-array. It walks the JSON once, by the rules of §3.4 and §3.5; nothing in the mapping language needs the JSON-LD expansion algorithm.
